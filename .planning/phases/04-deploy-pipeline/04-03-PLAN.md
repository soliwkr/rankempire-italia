<!-- Pattern retry loop da implementare (D-09 CONTEXT) -->
```typescript
async function waitForRepo(
  owner: string, repo: string, token: string,
  maxAttempts = 10, intervalMs = 500
): Promise<boolean> {
  for (let i = 0; i < maxAttempts; i++) {
    const res = await fetch(`https://api.github.com/repos/${owner}/${repo}`, {
      headers: {
        'Authorization': `Bearer ${token}`,
        'Accept': 'application/vnd.github+json',
        'X-GitHub-Api-Version': '2022-11-28',
        'User-Agent': 'Rank-and-Rent-Factory-Core'
      }
    });
    if (res.ok) return true;
    await new Promise(resolve => setTimeout(resolve, intervalMs));
  }
  return false;
}
```

        githubRepo: string,

      ): Promise<CloudflarePagesProject> {
        const body = {

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CloudflarePagesService → CF API | CF_API_TOKEN (Cloudflare global token Pages:Edit + Account:Read) — mai loggato o esposto |
| GitHubService → GitHub API | GITHUB_TOKEN (fine-grained token repo:write) — mai loggato |
| retry loop → GitHub API | 10 chiamate GET /repos — non aumenta superficie di attacco ma crea traffico API ripetuto |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-03-01 | Information Disclosure | CF_API_TOKEN in log | mitigate | Il catch block di CloudflarePagesService fa `throw new Error(...)` — l'error message contiene solo status code e body CF API, MAI il token. Acceptance criteria: nessun `this.config.apiToken` in stringhe di log o error message |
| T-04-03-02 | Information Disclosure | GITHUB_TOKEN in retry loop error | mitigate | `waitForRepo` usa `this.config.token` solo nell'header fetch, MAI in stringhe di log. Il throw usa solo `owner/repo` names |
| T-04-03-03 | Denial of Service | retry loop (10×500ms = 5s) | accept | Limite fisso di 10 tentativi non espandibile da input esterno — parametri `maxAttempts`/`intervalMs` sono hardcoded al call site nel metodo `createProjectRepo`, non dal request body |
| T-04-03-04 | Spoofing | CF Pages project name injection | mitigate | `name: rr-${slug}` — slug viene dal D1 database (non da user input diretto al deploy endpoint). Slug è validato al momento della creazione progetto. In `projects.ts` deploy endpoint (piano 04-05) aggiungere validazione slug format `/^[a-z0-9-]+$/` prima di passare a CloudflarePagesService |
| T-04-03-05 | SSRF | URL iniettata in CloudflarePagesService | accept | L'URL `https://api.cloudflare.com/client/v4/accounts/${accountId}/pages/projects` è hardcoded — `accountId` viene da env var CF_ACCOUNT_ID, non da user input. Nessun SSRF possibile |
</threat_model>
